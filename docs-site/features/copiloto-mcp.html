Por que isto é barato — e por que só aqui

A regra de ouro nº 3 do template diz que toda lógica vive em Actions dentro do módulo dono, e que os canais — REST, MCP, linha de comando — são adaptadores finos sobre as mesmas Actions.

Na maioria dos projetos essa frase é ideologia de arquiteto. Aqui ela vira dinheiro na mesa: como cada regra já está numa Action, expor o sistema a uma IA é escrever uma camada de tradução, não reimplementar o produto. Num projeto com a lógica dentro dos controllers, esta página seria impossível de entregar numa madrugada — seria reescrever tudo. É o argumento mais concreto que a dupla tem para defender a escolha de arquitetura na banca.

O contexto que torna a resposta boa não é o modelo, é o acervo. Qualquer IA explica séries de Taylor. Só esta sabe que na prova do prof. Silva, em 2024/1, caiu quase só série — porque três veteranos escreveram isso, e o aluno está matriculado naquela disciplina. O CampusOS não compete com a IA; ele é a memória que faltava a ela.
routes/ai.php + app/Mcp/ — no app host, não em módulo✅ B8

MCP não é um módulo de domínio e não deve virar um. Ele não possui tabela, não tem regra de negócio própria e não é um bounded context — é um canal, como o HTTP. Mora no app host (app/Mcp/), junto do middleware de borda, e cada tool é uma classe que chama uma Action de módulo. 

// Forma de toda tool — nada além de tradução:
final class MyProgress
{
    public function __construct(private GetProgressAction $action) {}

    public function handle(array $input): array
    {
        // o contexto de tenant/usuário já foi resolvido na autenticação
        // do canal -- a tool não decide quem é ninguém.
        return $this->action->execute(new GetProgressInput(...$input))->toArray();
    }
}
Se uma tool precisar de um if de regra de negócio, pare. Isso é sinal de que a regra não existe na Action — e a versão REST da mesma funcionalidade vai acabar com a regra escrita de novo, ligeiramente diferente. Empurre para a Action e chame de lá. É a fronteira que o ArchTest não consegue verificar sozinho, e a que mais se fura sob pressão de horário.

Seis de leitura, uma de escrita. É a mesma decisão tomada no LifeOS original do Psyches Archive, e pelo mesmo motivo: leitura errada é ruído, escrita errada é dado corrompido em cima de histórico acadêmico. A tool de escrita é a de menor consequência do sistema — e criar anotação é justamente o que se quer fazer no meio de uma conversa de estudo. Nenhuma tool toca matrícula, nota ou horas.

Cada tool declara nome, descrição e schema de entrada; o retorno é o mesmo DTO que o Resource HTTP serializa. Duas regras não negociáveis, herdadas do canal REST:

  1. O escopo de visibilidade é o mesmo. acervo_da_disciplina passa pelo NoteVisibilityScope igual ao endpoint. Um canal que enxerga mais que o outro é um vazamento, e é o erro clássico de adicionar um canal novo depressa.
  2. O tenant é restaurado explicitamente. MCP não tem sessão HTTP — TenantContext::runAs() na autenticação do canal, exatamente como nos Jobs (regra de ouro nº 4).
Autenticação do canal

Token por usuário, trocável, com escopo de leitura — e a tool de escrita exigindo um escopo separado. Não repita o atalho do LifeOS original, que cravou o token no código-fonte: lá era um sistema pessoal de um usuário só; aqui são N alunos de N instituições, e um token compartilhado seria um vazamento cross-tenant com passo único.

Antes de encarar este bloco às 13h da tarde: ele é a terceira esticada por um motivo. O efeito no pitch é o maior da lista, e o risco de consumir duas horas é igualmente o maior — configurar autenticação de um canal novo é onde o tempo some. Só comece se B1–B7 fechou inteiro. Se começar e travar aos 40 minutos, abandone sem dó: o restante da demo não depende disto.

Tem 35 anotações de veteranos nessa disciplina. As três mais votadas dizem a mesma coisa: a P2 do prof. Silva cobra séries numéricas e de potências, com pouca integral imprópria. Um resumo de 2024/1 traz os critérios de convergência numa página; uma lista de 2026/1 tem 18 exercícios resolvidos, quase todos de séries.

Começaria pela lista — se travar em algum critério, o resumo cobre.

Nenhuma frase dessa resposta veio de um modelo treinado na internet: prazo, autoria, semestre e conteúdo saíram de tabelas do CampusOS. É o que faz a demonstração fechar — e é por isso que ela é o último tempo do roteiro, quando ela existe.

Se o MCP não ficar pronto, isto ainda é pitch. A arquitetura de Actions é verdade com ou sem o canal — e "as regras já estão prontas para isso, é o próximo canal a plugar" é uma frase forte na banca, contanto que seja dita como roadmap e não como entrega. Nunca demonstre com tela de mentira. Um jurado que percebe vale menos que dez features faltando.
