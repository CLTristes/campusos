Fluxos multi-etapa, em diagrama

A maior parte do CampusOS não é CRUD — é uma chamada que dispara uma cascata. O exemplo mais rico é o envio do histórico acadêmico: um POST vira upload, fila, leitura por IA, conferência humana e só então matrícula de verdade, com pontos de decisão em cada etapa. Esta página traça, em sequência e em máquina de estado, os seis fluxos onde entender "o que acontece por baixo de uma chamada só" é o que faz desenhar a tela certa da primeira vez.

1

Documento acadêmico — a cascata mais longa do sistema

Um POST síncrono cria o registro e devolve 202 na hora — tudo que vem depois roda em fila, em outro processo, sem o cliente esperando. É por isso que o front precisa fazer polling: não existe um único "aguarde" que cubra da leitura por IA até a matrícula existir de fato.

sequência
sequenceDiagram
    actor Aluno
    participant API as AcademicDocumentController
    participant Upload as UploadAcademicDocumentAction
    participant Fila as ParseAcademicDocumentJob (fila imports)
    participant IA as AcademicDocumentExtractor
    participant Confirm as ConfirmAcademicDocumentAction
    participant DB as Banco (transação)

    Aluno->>API: POST /me/academic-documents
    API->>Upload: execute()
    Upload->>DB: EnrollmentRequest (status=uploaded)
    Upload-->>Fila: dispatch()
    API-->>Aluno: 202 Accepted

    activate Fila
    Fila->>DB: status=processing
    Fila->>IA: extract(arquivo)
    alt indisponibilidade (5xx, 429, timeout, sem credencial)
        IA-->>Fila: ExtractorUnavailableException
        Fila->>DB: status=uploaded (reset)
        Fila--xFila: relança — fila reprocessa (3 tries, backoff 10s/60s)
    else recusa de negócio (não é documento acadêmico, sem disciplinas)
        IA-->>Fila: ExtractedDocument::failed()
        Fila->>DB: status=failed (final, sem retry)
    else sucesso
        IA-->>Fila: ExtractedDocument (lines[])
        Fila->>DB: status=parsed + erq_extraction
    end
    deactivate Fila

    Aluno->>API: GET /me/academic-documents/{id} (polling)
    API-->>Aluno: status atual

    Aluno->>API: POST .../confirm (lines conferidas)
    API->>Confirm: execute()
    activate Confirm
    Confirm->>DB: BEGIN
    loop cada linha
        alt disciplina não catalogada OU status não reconhecido
            Confirm-->>Confirm: entra em pending[], não aborta
        else linha válida
            Confirm->>DB: SubjectEnrollment (updateOrCreate)
        end
    end
    Confirm->>DB: EnrollmentRequest status=confirmed
    Confirm->>DB: COMMIT
    deactivate Confirm
    API-->>Aluno: 200 { imported, pending[] }
máquina de estado — DocumentRequestStatus
stateDiagram-v2
    [*] --> uploaded: POST /me/academic-documents
    uploaded --> processing: Job pega da fila
    processing --> uploaded: exceção de transporte (relança, reprocessa)
    processing --> failed: recusa de negócio (sem retry)
    processing --> failed: esgotou 3 tries (falha do Job)
    processing --> parsed: extração ok
    parsed --> confirmed: POST .../confirm
    confirmed --> [*]
    failed --> [*]
Confirmar duas vezes é 422, não um segundo import. ConfirmAcademicDocumentAction recusa de cara se erq_status já é confirmed. E dentro da transação, uma linha com disciplina fora do catálogo ou status de histórico não reconhecido NUNCA aborta as outras — vira uma entrada em pending[] pro aluno resolver, enquanto o resto da matrícula é criado normalmente.
2

Adoção de tarefa da turma

O ponto central: adotar cria uma cópia, nunca compartilha a linha original. Sem isso, o primeiro aluno que marcasse "concluída" concluiria a tarefa pra turma inteira.

sequência
sequenceDiagram
    actor Aluno
    participant API as TaskController
    participant Action as AdoptTaskAction
    participant DB as Banco

    Aluno->>API: POST /tasks/{id}/adopt
    API->>Action: execute()
    Action->>DB: Task::findOrFail(origem)
    alt tarefa está private
        Action-->>API: 403 — "não foi compartilhada com a turma"
    else o próprio dono tentando adotar a si mesmo
        Action-->>API: 422 — "você já é o dono desta tarefa"
    else ok
        Action->>DB: firstOrCreate(owner, origin_tsk_id) — cópia, visibility=private
        Note over DB: índice único (owner, origin) é a rede de
segurança contra corrida — a idempotência
de aplicação já resolve o duplo clique comum
        Action-->>API: 200, a cópia
    end
Chamar duas vezes não gera duas cópias. firstOrCreate procura por (owner_usr_id, origin_tsk_id) antes de inserir — encontra a cópia já existente e devolve ela. O índice único do banco é o que garante isso mesmo sob duas requisições simultâneas, quando a leitura de ambas ainda não viu a inserção uma da outra.
3

Escada de visibilidade da anotação

Cinco níveis, um vocabulário só (o mesmo enum Visibility que Task reaproveita). O detalhe que surpreende: não existe hierarquia de "só sobe". Qualquer transição em qualquer direção é permitida — a única guarda é não deixar a nota "presa" sem o dado que aquele nível exige.

máquina de estado — Visibility (Note e Task)
stateDiagram-v2
    [*] --> private: nasce (Note sempre; Task pode nascer em offering)
    private --> offering: precisa de offering_id
    private --> subject: precisa de subject_id
    private --> course: precisa de course_id
    private --> institution
    offering --> subject
    offering --> course
    offering --> institution
    offering --> private: despublicar — sempre permitido
    subject --> course
    subject --> institution
    subject --> private
    subject --> offering
    course --> institution
    course --> private
    course --> offering
    course --> subject
    institution --> private
    institution --> offering
    institution --> subject
    institution --> course
Despublicar nunca tem pré-condição. Voltar pra private de qualquer nível sempre funciona — as três validações (precisa de offering/subject/course) existem só pra impedir "publicar sem endereço", nunca pra impedir recuar.
4

Horas complementares — o corte por teto

Uma Action fina na escrita; o cálculo interessante mora inteiramente na leitura, recalculado a cada request — nunca persistido.

sequência
sequenceDiagram
    actor Aluno
    participant API as ComplementaryActivityController
    participant Action as CreateComplementaryActivityAction
    participant RM as ComplementaryHoursReadModel
    participant DB as Banco

    Aluno->>API: POST /me/complementary-activities
    API->>Action: execute()
    alt categoria de outra matriz
        Action-->>API: 422 — "categoria não pertence à sua matriz"
    else ok
        Action->>DB: ComplementaryActivity (status=submitted, sempre)
        API->>RM: summaryForCategory(registration, categoria)
        RM-->>API: granted = min(claimed, max_hours)
        API-->>Aluno: 201 { capped, hours_not_counted }
    end
O corte é por categoria, nunca por certificado. granted = min(soma_declarada, teto) agrega TODAS as atividades não-rejeitadas da categoria — não existe uma regra de "qual certificado perde a hora" que divida a perda entre linhas. cac_hours_granted na linha individual fica sempre null nesta entrega (reservado pra homologação futura).
5

Elegibilidade e simulação de reprovação

GET /me/next-term percorre o grafo de pré-requisitos uma vez. POST /me/simulate percorre o MESMO grafo duas vezes — uma com o histórico real, outra com a reprovação hipotética — e compara.

sequência
sequenceDiagram
    actor Aluno
    participant API as EligibilityController
    participant RM as EligibilityReadModel
    participant Action as SimulateFailureAction

    Aluno->>API: GET /me/next-term
    API->>RM: nextTerm(registration)
    loop cada disciplina não cursada
        RM->>RM: blockedReasons() — subject / corequisite / minimum_term / minimum_hours
    end
    RM-->>API: { eligible[], blocked[] com motivo }

    Aluno->>API: POST /me/simulate { fail: [códigos] }
    API->>Action: execute()
    Action->>RM: simulate(registration, fail[])
    RM->>RM: earliestPeriods(cenário REAL) — longest-path memoizado no DAG
    RM->>RM: earliestPeriods(cenário SEM as reprovadas)
    RM->>RM: compara os dois — disciplinas cuja projeção PIOROU entram em affected_subjects
    RM-->>API: { affected_subjects[], estimated_graduation_delay_terms }
    Note over API,RM: Nada é escrito no banco — tudo em memória,
dentro do mesmo request síncrono.
A disciplina reprovada nunca aparece como "afetada". Ela é a ENTRADA da simulação, não um efeito — affected_subjects só lista o que ficou pra depois POR CAUSA dela. minimum_hours não entra na projeção de período (não dá pra prever quanta hora cada período vai render), só nos bloqueios de next-term.
6

Chamada de tool via copiloto MCP

A mesma CreateNoteAction do REST, alcançada por um canal a mais — com uma camada de autorização extra que só essa tool específica precisa.

sequência
sequenceDiagram
    participant Cliente as Cliente MCP
    participant MW as auth:sanctum + tenant.user + abilities:mcp:read
    participant Server as CampusOsServer
    participant Tool as CriarAnotacaoTool
    participant Action as CreateNoteAction

    Cliente->>MW: POST /mcp (Bearer token)
    alt sem token válido
        MW-->>Cliente: 401
    else token sem ability mcp:read
        MW-->>Cliente: 403 — nenhuma tool roda
    else ok
        MW->>Server: despacha pra tool pedida
        Server->>Tool: handle(request)
        alt token sem ability mcp:write
            Tool-->>Cliente: erro — "sem permissão de escrita"
        else ok
            Tool->>Action: execute() — MESMA Action do REST
            Action-->>Tool: Note (sempre private)
            Tool-->>Cliente: dado estruturado
        end
    end
Duas checagens, não uma. abilities:mcp:read na rota barra o grosso antes de qualquer tool rodar; tokenCan('mcp:write') dentro do handle() de criar_anotacao é defesa em profundidade — e a única forma de testar essa regra pelo harness rápido do pacote, que não passa pelo middleware de rota de verdade.
Dois padrões que atravessam os seis fluxos. Toda Action roda o mesmo template method — sanitize → validate → authorize → handle (AbstractAction::execute(), no core). E todo AuditLog é gravado best-effort: se a escrita da auditoria falhar, a transação de negócio segue normalmente — auditoria nunca é motivo de a Action inteira falhar.
Achado, não corrigido nesta consolidação: não existe TaskObserver — ao contrário dos outros cinco fluxos de escrita, adotar uma tarefa (Fluxo 2) não parece gerar AuditLog. Fica registrado aqui como algo a decidir: lacuna ou decisão deliberada.
